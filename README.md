# Search+: Structuring Retrieved Context with Query-Aware Textual Graphs for Multi-Hop Retrieval

A research pipeline that augments passage retrieval for multi-hop question answering
using **LLM-extracted Knowledge Graphs** and **graph-traversal re-ranking**.
Evaluated on three public benchmarks: **MuSiQue**, **HotPotQA**, and **2WikiMultihopQA**.

## Overview

The system works as follows:

1. Raw passages for each QA question are downloaded from HuggingFace.
2. A local LLM (**Gemma 4** via Ollama) extracts a Knowledge Graph (nodes = passages, edges = inferred relations) for each question.
3. Those per-question KGs are merged with entity-overlap edges into a **hybrid graph**.
4. At retrieval time, a base ranker (BM25 or a dense encoder) scores all passages, and a graph algorithm (**BFS** or **Graph Embedding / GE**) re-ranks them by propagating scores through the graph structure.
5. A grid search on the validation split finds the best hyperparameters; the best config is then evaluated on the held-out test split.

## Dependencies & Installation

### Requirements

```
torch>=2.0
sentence-transformers>=3.0
rank-bm25>=0.2
ollama>=0.2
datasets>=2.18
numpy>=1.24
tqdm>=4.65
```

Save as `requirements.txt` and install with:

```bash
pip install -r requirements.txt
```

### Ollama (for KG extraction)

The KG mining step uses **Gemma 4** locally via [Ollama](https://ollama.com).

```bash
# Install Ollama (see https://ollama.com/download)
ollama pull gemma4:latest
```

`MineKG.py` will verify and pull the model automatically if it is not already present.

### GPU (optional)

All dense retrieval steps automatically use CUDA if available. The pipeline also runs on CPU, but will be significantly slower for large datasets.

## Pipeline

### Step 1 – Download Datasets

**2WikiMultihopQA**
```bash
python Dowload2Wiki.py
# Output: data/2wiki_validation.jsonl
```

**HotPotQA**
```bash
python DowloadHotPotQA.py
# Output: data/hotpotqa_validation.jsonl
```

**MuSiQue** – download manually from HuggingFace:
```python
from datasets import load_dataset
ds = load_dataset("allenai/musique", split="validation")
```
Save it to `data/musique_validation.jsonl` following the same schema used by the other two scripts
(`id`, `paragraphs`, `question`, `question_decomposition`, `answer`, `answer_aliases`, `answerable`).

---

### Step 2 – Split Datasets

Shuffles and splits every `.jsonl` file in `data/` into `_val` (2 000 records) and `_test` (2 000 records) splits.

```bash
python split_dataset.py
# Output: data/<stem>_val.jsonl  +  data/<stem>_test.jsonl
```

---

### Step 3 – Mine Knowledge Graphs

Uses a local **Gemma 4** model (via Ollama) to extract structured Knowledge Graphs from each passage.
All `.jsonl` files in `data/` are processed; one `_KG.json` file is written per input file.

```bash
python MineKG.py
# Input : data/*.jsonl
# Output: dataKG/<stem>_KG.json
```

Each output file is a JSON dictionary keyed by question `id`, with the structure:
```json
{
  "<question_id>": {
    "mode": "CONTEXT ONLY",
    "knowledge_graph": {
      "nodes": [...],
      "edges": [...]
    }
  }
}
```

Two extraction modes are available (toggle `use_question` in `MineKG.py`):
- `use_question=True` — KG is focused on what is relevant to answer the question.
- `use_question=False` *(default)* — KG is built from raw passage text only (broader coverage).

---

### Step 4 – Build Hybrid Graphs

Combine the per-question KGs from `dataKG/` with entity-overlap edges to produce
the **hybrid graph** files consumed by the validation and test scripts.

```bash
# Run your graph-builder script here
# Input : dataKG/<stem>_KG.json  +  data/<stem>_val.jsonl / _test.jsonl
# Output: graphs/<stem>_val_hybrid_graphs.json
#         graphs/<stem>_test_hybrid_graphs.json
```

Each hybrid graph file is a JSON dictionary keyed by question `id`, with the structure:
```json
{
  "<question_id>": {
    "nodes": [{"title": "...", "text": "...", "is_supporting": true}],
    "edges": [{"src": 0, "dst": 3, "relation_type": "kg_bridge"}]
  }
}
```

Two edge types are produced and can be selected independently at retrieval time:
- `"kg_bridge"` — relations inferred by the LLM (from KG triples).
- `"entity_overlap"` — edges between passages that share named entities.

---

### Step 5 – Validate (Grid Search)

Runs a full grid search over all retrieval methods and graph modes on the **validation** split.
Discovers the best hyperparameter configuration per method × graph-mode × graph-type combo.

```bash
python ValidateExperiments.py
# Input : data/*_val.jsonl  +  graphs/*_val_hybrid_graphs.json
# Output: results/results_<dataset>_val.json
```

**Graph modes searched:**

| Mode | Description |
|------|-------------|
| `none` | Pure base ranker (BM25 or dense), no graph |
| `bfs`  | BFS traversal seeded from top-K base results |
| `ge`   | Graph Embedding — iterative neighbour-score propagation |

**Graph types searched:** `all`, `triple`, `entity` (controls which edge types are active).

---

### Step 6 – Test (Held-out Evaluation)

Reads the best configs found in Step 5 and evaluates them on the **test** split.
Always recomputes from scratch (no cache).

```bash
python TestExperiments.py
# Input : results/results_<dataset>_val.json
#         data/*_test.jsonl
#         graphs/*_test_hybrid_graphs.json
# Output: results/test_predictions_<method>_<mode>_<type>_<dataset>.json
#         results/test_results_by_combo.json   (master summary, merged on each run)
```

The master summary (`test_results_by_combo.json`) accumulates results across all datasets
and is never overwritten — new results are merged in.

---

### Step 7 – Baseline Evaluation

`Evaluation_Gemma_Baseline.py` provides a lightweight **semantic baseline** report.
It reads pre-generated ranking JSONL files (one line per question, with `ranked` and `relevance` fields)
and computes Recall@K and FullRec@K for:

- **Baseline** — the original semantic ranking (BM25 / dense), with no graph component.
- **Filtered** — a simulated scenario where graph-unconnected nodes are demoted to the tail of the ranking.

The Δ between the two scenarios quantifies the structural contribution of the KG edges.

```bash
python Evaluation_Gemma_Baseline.py
# Input : results/2wiki_validation_test_run.jsonl
#         results/musique_validation_test_run.jsonl
#         results/hotpotqa_validation_test_run.jsonl
# Output: printed metrics report (stdout)
```

> **Note — "Gemma Baseline":** the name refers to the fact that these run files were produced
> by a retrieval pipeline whose KGs were mined by **Gemma 4**. The script itself is model-agnostic
> and can evaluate any ranking JSONL that follows the same schema.

## Configuration

All tuneable knobs live in `config.py`. Key settings:

| Variable | Description |
|----------|-------------|
| `DATA_DIR` | Path to the `data/` folder |
| `GRAPHS_DIR` | Path to the `graphs/` folder |
| `RESULTS_DIR` | Path to the `results/` folder |
| `MODEL_CONFIGS` | Dict of retriever names → model IDs and prefixes |
| `ENABLED_METHODS` | Toggle individual retrievers on/off |
| `GRID_GRAPH_TYPE` | List of edge-type filters to sweep (`all`, `triple`, `entity`) |
| `BFS_CONFIGS` / `GE_CONFIGS` | Hyperparameter grids for BFS and GE modes |
| `SAMPLE_SIZE` | Cap the number of items per dataset (set `None` for full run) |
| `PRIMARY_METRIC` | Metric used to pick the best config (e.g. `"FullRec@5"`) |

## Retrieval Methods

All retrievers are implemented in `retrievers_musique.py` and are also mirrored
inline in `ValidateExperiments.py` / `TestExperiments.py` for standalone execution.

| Retriever | Type | Description |
|-----------|------|-------------|
| `BM25Retriever` | Sparse | Classic BM25 over title + passage text |
| `EmbeddingRetriever` | Dense | Cosine similarity with a sentence-transformer model (e.g. `thenlper/gte-base`) |
| `HybridRetriever` | Hybrid | Linear interpolation of normalised BM25 + embedding scores |
| `graph_expand()` | Graph | BFS expansion from semantic seeds; supports `linear`, `geometric`, `harmonic`, and `rrf` scoring |

Dense models support per-model query and document prefixes (required for BGE, E5-family, etc.)
and are configured in `config.py` under `MODEL_CONFIGS`.

---

## Metrics

| Metric | Description |
|--------|-------------|
| `Recall@K` | Fraction of questions where ≥ 1 gold passage appears in the top-K |
| `FullRec@K` | Fraction of questions where **all** gold passages appear in the top-K |
| `NDCG@10` | Normalised Discounted Cumulative Gain at 10 |
| `MRR` | Mean Reciprocal Rank of the first gold passage |

`FullRec@K` is the primary metric used for hyperparameter selection (configurable via `PRIMARY_METRIC`).
